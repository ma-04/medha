# API contract

The backend is Supabase Postgres. Every piece of business logic lives in a
`SECURITY DEFINER` RPC, and every authorization decision is made by RLS policies
or by `is_admin()` / `can_author()` inside those RPCs. Nothing that matters is
enforced in Next.js.

That is the whole point of this document: **an Android client holding the anon
key and a user JWT can do everything the web app does, over the same endpoints,
with the same guarantees.** The web `requireUser()` / `requireStaff()` /
`requireAdmin()` helpers are navigation conveniences — they redirect — not the
security boundary. Deleting them would leak no data.

Two files are the authoritative machine-readable half of this contract:

- `src/types/database.ts` — generated by `supabase gen types typescript`. Table
  rows, RPC argument and return types. Generate Kotlin models from this, and
  regenerate it whenever a migration lands.
- `src/lib/scoring.ts` — the pure grading formula, mirroring `_grade_attempt()`
  in SQL. Useful for optimistic UI; the server number always wins.

## Endpoints

All RPCs are reachable at `POST /rest/v1/rpc/<name>` with `apikey: <anon key>`
and `Authorization: Bearer <user JWT>`. Arguments go in the JSON body under
their `p_`-prefixed names. Errors surface as PostgREST `400` with the
`raise exception` text in `message`; the tables below give those strings
verbatim, because they are the API's error codes.

### Exam flow

| RPC | Args | Returns |
|---|---|---|
| `start_exam_attempt` | `p_exam_id uuid` | `jsonb` |
| `retry_exam_attempt` | `p_exam_id uuid` | `jsonb` |
| `save_answer` | `p_attempt_id uuid, p_question_id uuid, p_selected_key text` | `void` |
| `submit_attempt` | `p_attempt_id uuid` | `jsonb` |
| `get_attempt_review` | `p_attempt_id uuid` | `setof record` |
| `get_leaderboard` | `p_exam_id uuid` | `setof record` |

**`start_exam_attempt`** creates attempt #1 or resumes the latest one, then
returns the exam in full:

```json
{
  "attempt_id": "uuid",
  "deadline": "timestamptz",
  "submitted_at": "timestamptz | null",
  "server_now": "timestamptz",
  "answers": { "<question_id>": "<selected_key>" },
  "questions": [{ "id", "order_index", "subject_id", "body", "options",
                  "image_url", "source_label" }]
}
```

`questions` never carries `correct_key` — the correct answers live in
`question_answers`, which no student can read (see the RLS matrix). Trust
`server_now` and `deadline`, not the device clock: compute the countdown as
`deadline − server_now` and tick locally from there. A phone with a skewed clock
must not get more time, and it won't, because `save_answer` re-checks the
deadline server-side anyway.

Raises `not authenticated`, `exam not found`, `exam not available`,
`exam has not started`, `exam has ended`. For `live` exams the deadline is
clamped to `exams.ends_at`, so a late joiner gets less time rather than an
extension.

**`retry_exam_attempt`** starts attempt N+1 for a `model` exam and returns
`{ attempt_id, attempt_number }`. Guarded on: exam is `model` and `published`,
a previous attempt exists and was submitted, and the attempt count is below
`exams.max_attempts`. Raises `retry not allowed`, `no attempt to retry`,
`finish your current attempt first`, `no attempts left`. Call
`start_exam_attempt` afterwards to load the questions.

**`save_answer`** upserts one answer; passing `p_selected_key = null` clears it.
Refuses to write when the attempt is not yours, is already submitted, is past
its `deadline` (`time is up`), or when the question does not belong to that exam
(`question not in exam`). Safe to call on every tap.

**`submit_attempt`** grades server-side and returns
`{ attempt_id, score, correct_count, wrong_count, skipped_count,
subject_breakdown, submitted_at }`. Idempotent: a second call re-reads the
stored row rather than re-grading. `subject_breakdown` is keyed by `subject_id`
with `{ total, correct, wrong, skipped }`.

**`get_attempt_review`** returns one row per exam question with both
`selected_key` and `correct_key`. It is the *only* way a student ever sees a
correct key for an exam question, and it refuses until the answers are final:
for `model` exams the attempt must be submitted (`attempt not submitted yet`),
for `live` exams `exams.results_published_at` must be set
(`results not published yet`). Admins bypass both checks.

**`get_leaderboard`** returns `rank, user_id, full_name, score, is_self` for the
top 100 plus the caller's own row, ordered by rank. Raises
`results not published yet` until `results_published_at` is set (admins bypass).
`full_name` falls back to `পরীক্ষার্থী`.

### Practice and archive

| RPC | Args | Returns |
|---|---|---|
| `check_practice_answer` | `p_question_id uuid, p_selected_key text` | `correct_key, is_correct, explanation` |
| `reveal_answer` | `p_question_id uuid` | `correct_key, explanation` |

Both require a session (`not authenticated`) and both refuse questions that are
not `published` (`question not available`). `check_practice_answer` also records
the attempt in `practice_answers`, which is what drives the per-topic stats on
the home screen — so the client must call it rather than grading locally, or the
stats silently stop accruing.

### Auth predicates

| RPC | Returns | Meaning |
|---|---|---|
| `is_admin()` | `boolean` | caller's `profiles.role = 'admin'` |
| `can_author()` | `boolean` | caller's `profiles.role in ('admin', 'teacher')` |

Both are `STABLE SECURITY DEFINER` and are called from inside RLS policy
expressions, so `authenticated` must keep `EXECUTE` on them. They read
`public.profiles` — never `auth.users.user_metadata`, which is user-writable and
must never be trusted for authorization.

A client can call them directly to decide what UI to show. That is a hint, not a
gate: every privileged operation re-checks.

### Staff-only

| RPC | Args | Returns | Gate |
|---|---|---|---|
| `admin_upsert_question` | `p_topic_id, p_body, p_options, p_correct_key, p_id?, p_explanation?, p_image_url?, p_difficulty?, p_source_exam?, p_source_year?, p_source_label?, p_status?` | `uuid` | `can_author()` |
| `admin_set_exam_questions` | `p_exam_id uuid, p_question_ids uuid[]` | `integer` | `can_author()` |
| `admin_import_questions` | `p_rows jsonb` | `jsonb` | `can_author()` |

All three raise `not authorized` for anyone else.

`admin_set_exam_questions` replaces the exam's whole question set in order,
derives each `subject_id` from the question's topic, and rewrites
`pattern.total_questions`. Returns the new count.

`admin_import_questions` takes an array of rows and returns
`{ inserted, updated, errors: [{ row, error }] }`. Dedupe is by
`questions.content_hash`, a unique column holding
`sha256("<source_exam>::<trimmed body>")`; a row whose hash already exists is
updated, not duplicated, so `inserted` is 0 on a repeat import. Each row is:

```json
{ "row": 1, "subject_slug": "math", "topic_slug": "algebra",
  "body": "...", "options": [{ "key": "a", "text": "..." }],
  "correct_key": "a", "explanation": null, "difficulty": null,
  "source_exam": null, "source_year": null, "source_label": null,
  "status": "published" }
```

`row` is echoed back in `errors` so the caller can point at the offending input
line. A row that fails (unknown topic, `correct_key` not among the options,
fewer than two options, or any SQL error) is skipped without aborting the rest.
Option keys must be lowercase `a`–`e`; the web client normalizes CSV in
`src/lib/import.ts` before calling, and a native client must do the same.

The web route `POST /api/admin/import` is a thin wrapper that validates shape
with zod and forwards to this RPC on the caller's session. Android can skip it
and call the RPC directly.

### Not callable by clients

`_grade_attempt`, `auto_submit_expired`, `auto_finalize_live`, and
`finalize_live_exam` have `EXECUTE` revoked from `anon` and `authenticated`.
Before that revoke they were reachable at `/rest/v1/rpc/<name>` with nothing but
the anon key, and three of them took no arguments.

`auto_submit_expired` and `auto_finalize_live` run every minute under `pg_cron`
as `postgres`, which owns them; a function's owner keeps `EXECUTE` implicitly,
which is why revoking the `PUBLIC` grant did not break the schedule. Live exams
therefore finalize themselves — no client ever needs to ask.

## RLS matrix

Every table in `public` has RLS enabled. `anon` matches only the `SELECT`
policies with no `TO` clause, which is deliberate: the marketing home page
renders for signed-out visitors and queries `exams`.

| Table | SELECT | INSERT / UPDATE / DELETE |
|---|---|---|
| `subjects` | anyone | `can_author()` |
| `topics` | anyone | `can_author()` |
| `questions` | `status = 'published'`, or `can_author()` | `can_author()` |
| `exams` | `status in (scheduled, published, archived)`, or `can_author()` | `can_author()` |
| `profiles` | own row, or `is_admin()` | own row, or `is_admin()` |
| `exam_attempts` | own rows, or `is_admin()` | **none** |
| `practice_answers` | own rows | INSERT own rows only |
| `question_answers` | `can_author()` | `can_author()` |
| `exam_questions` | `can_author()` | `can_author()` |
| `attempt_answers` | `can_author()` | `can_author()` |

Read the last four rows together with `exam_attempts`. They are the integrity
core:

- **Correct keys are unreachable.** `question_answers` is staff-only for both
  read and write. A student obtains a correct key only through
  `get_attempt_review`, `check_practice_answer`, or `reveal_answer`, each of
  which decides for itself whether the answer may be shown yet.
- **Scores are untamperable.** `exam_attempts` has a `SELECT` policy and *no*
  write policy at all. Students cannot insert, update, or delete an attempt
  through PostgREST; `score`, `deadline`, `submitted_at`, and `rank` change only
  inside `SECURITY DEFINER` RPCs.
- **Answers are untamperable.** `attempt_answers` is likewise staff-only
  directly, writable by students only via `save_answer`, which enforces
  ownership, submission state, the deadline, and exam membership.
- **The question set is hidden.** `exam_questions` is staff-only, so the exam's
  composition arrives only in `start_exam_attempt`'s response, already stripped
  of answers.

`profiles.role` and `profiles.plan` are additionally pinned by the
`protect_profile_columns()` trigger, so the own-row `UPDATE` policy cannot be
used to self-promote to admin.

### Storage

Bucket `question-images` is public-read. Writes (`INSERT`, `UPDATE`, `DELETE`)
require `can_author()`. Upload with the storage API and store the resulting
public URL in `questions.image_url`.

## What Android reimplements

Most of the client port is mechanical — same RPCs, same arguments. These four
things have no portable equivalent and must be rebuilt natively rather than
translated:

**Session storage.** The web relies on `@supabase/ssr` writing httpOnly cookies
and a middleware that refreshes them on every request. The Kotlin SDK
(`supabase-kt`) owns its own session store and refresh loop. There is nothing to
port from `src/lib/supabase/` — instantiate the client per the Kotlin SDK's
guidance and let it manage the token.

**OAuth redirect.** `src/app/(auth)/actions.ts` sends the provider to
`${origin}/auth/callback`, a route handler that exchanges the code for a
session. On Android this becomes a deep link (an app-scheme or App Links
redirect URL) registered in the Supabase dashboard's redirect allowlist; the
Kotlin SDK handles the exchange. The `/auth/callback` route is web-only.

**Route guarding.** `src/lib/supabase/middleware.ts` gates `/admin`, `/profile`,
`/exams`, `/live`, `/practice` on a valid JWT. Navigation guarding is a UI
concern — implement it however the navigation graph prefers. It grants no
access; the RLS matrix above is what actually protects the data.

**Locale.** The web reads a `locale` cookie, which a mobile app has no analogue
for. Read `profiles.preferred_locale` instead. `src/app/actions/locale.ts`
already persists it there on every switch, so the two clients stay in sync for
free.

Everything else — the scoring formula, the deadline arithmetic, the retry cap,
the reveal rules — is already server-side. Do not reimplement it on the client.
If a rule ever appears to need porting, that is a signal the rule leaked out of
Postgres and should be pushed back in.
